1. Executive Summary

Modern digital retail platforms face an unprecedented challenge known as catalog overload. With tens of thousands of unique stock keeping units (SKUs) available online, human cognitive bandwidth is insufficient to discover relevant items manually. Consequently, personalized recommendation systems have evolved from auxiliary e-commerce features into foundational revenue drivers. However, real-world retail transaction histories are notoriously sparse, skewed, and predominantly implicit—lacking explicit 1-to-5 star ratings while reflecting purchases, returns, wholesale orders, and system noise.

This project presents the engineering and empirical validation of an end-to-end, big-data recommendation engine developed with Python, Apache Spark (PySpark), and Streamlit. Utilizing the transnational UCI Online Retail dataset comprising 541,909 transactional records, we design a modular data pipeline that conducts systematic data quality profiling, eliminates operational noise (149,217 defective records removed), and constructs an implicit customer-product interaction matrix of 266,110 pairs across 4,334 verified customers and 3,657 product items.

2. Problem Statement & Motivation

When e-commerce platforms expand their catalogs, customer search friction escalates exponentially. Customers exhibit choice overload (the Paradox of Choice), resulting in shopping cart abandonment and high bounce rates. Traditional navigational search requires the customer to already know the exact product name or category, rendering discovery of complementary or long-tail products nearly impossible.

Academic literature often demonstrates recommendation algorithms on explicit rating datasets (such as MovieLens 1M/20M or Netflix Prize). In commercial retail, however, less than 2% of shoppers ever submit numerical reviews. Instead, e-commerce data consists almost entirely of transactional logs: invoice IDs, item codes, purchased quantities, and timestamps. Crucially, implicit data possesses no negative feedback: the absence of a purchase does not imply customer distaste; it almost always indicates lack of awareness.

4. Data Profiling & Cleaning Pipeline

The raw dataset consists of 541,909 records. Automated quality auditing identified severe data anomalies that would corrupt machine learning models if left untreated:

  • Missing Customer IDs (135,080 rows / 24.9%): Guest checkouts lacking customer accounts cannot be personalized via collaborative filtering.
  • Cancelled Invoices (9,288 rows): Invoices starting with 'C' indicate returns, cancellations, and credit refunds.
  • Non-Positive Quantities (10,624 rows): Negative values represent inventory damage, lost stock, and stock adjustments.
  • Non-Positive Unit Prices (2,517 rows): Prices <= £0 indicate promotional samples, bad debt, or company write-offs.
  • Duplicate Transactions (5,268 rows): Exact duplicate rows from browser re-submissions or sync glitches.

Our PySpark cleaning script purged all 149,217 defective records, producing exactly 392,692 high-integrity transactions.

Windows Platform Compatibility Workaround: On Windows, Spark's native df.write.csv() requires Hadoop winutils.exe and throws UnsatisfiedLinkError. We engineered an incremental streaming exporter using df.toLocalIterator() and Python's built-in csv.writer. This streams partition rows sequentially to disk, avoiding memory bloat and operating smoothly without Hadoop dependencies.

5. Feature Engineering: The Implicit Interaction Matrix

In script 06_create_interactions.py, we aggregated transactions at the (CustomerID, StockCode) level after filtering out 8 administrative non-product fees (postage, carriage, bank charges, manual entries, amazon fees, etc.).

To define interaction strength, we selected the logarithmic scaling of distinct purchase orders:

r_{u,i} = ln(1 + PurchaseCount_{u,i})

Theoretical Justification: Distinct order frequency represents true sustained customer preference far better than raw units purchased in a single order (which often reflects one-off accidental bulk buys or wholesale discounting). Applying ln(1 + x) enforces diminishing marginal returns and prevents high-volume purchasers from distorting ALS gradient descent.

6. Machine Learning Model Design: Spark MLlib ALS

We trained an Alternating Least Squares (ALS) Matrix Factorization model under the Hu-Koren-Volinsky implicit feedback formulation:

min_{U,V} ∑_{u,i} c_{u,i} ( p_{u,i} - u_u^T v_i )^2  +  λ ( ∑_u ||u_u||^2 + ∑_i ||v_i||^2 )
  • Binary Preference p_{u,i}: 1 if r_{u,i} > 0, 0 if unobserved.
  • Confidence Weight c_{u,i}: 1 + α · r_{u,i} (with α = 1.0). Zero interactions carry base confidence 1; purchases scale up confidence.
  • Latent Factors (rank = 20): Captures 20 hidden preference dimensions (vintage decor, kitchen accessories, novelty toys).
  • Regularization (λ = 0.1): L2 penalty preventing parameter vector explosion.
  • Non-Negative Constraint (nonnegative = True): Forces factor matrices to be non-negative, yielding additive, interpretable part-based customer preferences.

9. Viva Voce & Oral Defense Handbook (Key Q&As)

Q1: Why did you choose Collaborative Filtering instead of Content-Based Filtering?
Collaborative filtering discovers latent, cross-category relationships across user shopping behaviors without requiring hand-crafted product feature tagging. It discovers that buyers of vintage clocks also buy floral teacups, even if their metadata keywords share nothing in common.
Q2: Why did you use log1p(PurchaseCount) instead of raw quantity?
Wholesale buyers often purchase 500 units in a single order, which would dominate the matrix. Distinct order count reflects true sustained preference. Applying ln(1 + count) enforces diminishing marginal returns and stabilizes gradient descent.
Q3: Why ALS over Stochastic Gradient Descent (SGD)?
In distributed clusters like Apache Spark, SGD requires sequential parameter updates, creating network synchronization locks. ALS turns a non-convex problem into independent quadratic sub-problems solvable in closed form in parallel across Spark worker nodes without inter-thread locking.
Q4: Why evaluate using Precision@10 / Recall@10 instead of RMSE?
In implicit feedback, RMSE is mathematically meaningless because unobserved items are not negative ratings—they are mostly unseen items. A model predicting zero for all unseen items gets a great RMSE but zero practical utility. In real retail, users only see the Top-N items on screen, making ranking accuracy the true test of commercial value.
Q5: How does your system handle the Cold Start Problem?
In offline evaluation, we configure coldStartStrategy='drop'. In production, we employ a hierarchical fallback: known users receive personalized ALS recommendations; new users with zero history receive the Global or Country-Specific Popularity recommendations precomputed in script 10.
Q6: What were your quantitative benchmark results?
Across 4,026 test users, ALS achieved 11.81% Precision@10 and 11.45% Recall@10, outperforming the Global Popularity baseline (4.35% Precision@10, 3.83% Recall@10) by 2.71x and 2.99x respectively.
Q7: How did you handle alphanumeric StockCodes in Spark MLlib?
Spark ALS strictly requires integer user and item IDs. We used Spark's StringIndexer to map alphanumeric StockCodes into 0-indexed integer itemIds, and maintained a product_id_mapping table to translate predictions back to original SKUs.
Q8: How did you bypass Windows Hadoop winutils errors?
Spark's native write relies on Hadoop winutils.exe on Windows. We avoided this dependency entirely by streaming records partition-by-partition using df.toLocalIterator() directly into Python's native csv.writer, ensuring memory safety and 100% platform independence.

This project successfully engineered and empirically validated an industrial-grade E-Commerce Recommendation System using Apache Spark ALS, PySpark, and Streamlit. By addressing the critical realities of commercial retail data—implicit signals, high catalog sparsity (98.32%), wholesale purchase skew, and operational noise—the pipeline transforms raw transaction logs into an accurate, high-speed personalization engine.
